# 研发自测方式分享：用测试用例脑图把交付质量前置

> 面向研发同事，不要求熟悉测试理论，只讲怎么用、为什么这样用。
> 基于 ai-mind-map 项目当前能力整理，核心思路：**用例不只是 QA 的资产，而是研发自测的工作台**。

---

## 一、为什么要这样做

### 研发自测常见的痛点

| 问题 | 原因 |
|------|------|
| 不知道测什么 | 没有“测试点”概念，只凭感觉点一点 |
| 测了但不完整 | 没有按风险分层，漏掉异常流和数据一致性 |
| 用例散落在文档/聊天记录里 | 没有统一入口，改完需求也不更新 |
| 自测结果说不清楚 | 没有“通过/失败/阻塞”的明确标记和记录 |
| QA 接手时要重新理解 | 研发和测试之间缺少共享的用例资产 |

### 这个项目解决什么

把测试用例做成**可维护、可追溯、可执行的脑图资产**：

- 研发在开发过程中按用例自测，而不是凭感觉。
- 交付时 QA 直接看同一份脑图，不用重新整理。
- AI 辅助生成和补充用例，人负责确认优先级和覆盖。
- 用例有稳定的 ID 和来源，需求变更时能快速定位受影响范围。

---

## 二、核心工作流

### 1. 从需求到测试点（不是从需求到用例）

先想清楚“要验证什么、为什么、依据什么判断”，再写用例。

最小测试分析模板：

```text
测试对象：哪个功能/接口/数据流被改动？
事实来源：需求 §X / 接口文档 §Y / 代码路径
范围：本次覆盖什么，不覆盖什么
测试条件：哪些行为必须被独立验证？
判定依据：通过/失败怎么判断？
风险：失败影响什么？能不能恢复？
```

测试条件 ≠ 用例。一个条件可能对应 1-3 条用例，用例验证的是“条件在不同状态/输入下的表现”。

### 2. 分层原则

第一层按**执行入口**（超管端/企业端/APP/迁移工具），不按测试方法。

第二层按**稳定业务能力或状态**（开通、检测、迁移、切换、回收站），不按数据类型或接口名。

用例叶子标题写“条件 + 动作 + 主要结果”：

```text
✅ 企业停止使用后查看资格，不自动撤回或切回平台存储
✅ 迁移 5GB 大文件，分片完成后文件内容保持一致
❌ 上传功能测试（无动作/无结果）
❌ 验证 INTERNAL_PENDING 状态下 record 更新（实现词）
```

### 3. 用例字段规范

每条用例至少有：

| 字段 | 说明 |
|------|------|
| `text` | 标题，条件+动作+主要结果，一眼能看懂 |
| `priority` | P0-P3，按业务风险定，不是“正常=P0” |
| `precondition` | 执行前状态，没有就写“无” |
| `steps` | 可执行动作，不是“按需求操作” |
| `expected` | 可观察、可判定的结果，禁止“功能正常” |
| `caseType` | functional/boundary/exception/security/data… |
| `testLevel` | ui/api/service/database/contract/e2e |
| `remark` | `CASE-*` + 来源 + `TCND-*`，必要时写定级依据 |

P0 额外要求备注写清：**影响 → 范围 → 恢复 → 发布决策**。

### 4. 追溯 ID 规则

- `CASE-*`：全文档唯一，复用到不同用例是 ERROR。
- `TCND-*`：一个可独立验证的行为/风险，不是模块名；同一条件超 4 条用例说明条件太粗。

这两条由 `validate-test-cases.js` 自动检查，AI 生成时也会遵守。

## 三、AI 怎么帮你

### 场景 A：从需求文档生成用例脑图

在应用里打开 AI 助手，直接说：

```text
读取 /path/to/需求文档.md，
用 create_document 新建一篇「XXX 测试用例」脑图，
一级按执行入口（超管/企业/APP）分组，
每个功能点建 TCND 测试条件，
用例带 priority/expected/remark(CASE-* + 来源 + TCND-*)。
```

AI 会通过 MCP 工具直接写入脑图，应用实时刷新。

### 场景 B：补充或评审已有用例

```text
打开 XX 脑图，只读评审：
- 找出覆盖缺口（哪个来源没有对应用例）
- 找出重复 CASE-ID 或过粗 TCND
- 找出 P0/P1 定级不合理的用例
先报告，不要直接改。
```

### 场景 C：需求变更后增量维护

```text
需求 XX 从 A 改为 B，
在 XX 脑图里找出受影响的用例，
更新或新增，保留未受影响的 CASE-ID。
```

AI 按 traceability-standard 保留稳定 ID，只更新受影响部分。

## 四、质量门禁

写入后必须跑确定性校验：

```bash
node .agents/skills/test-case-designer/scripts/validate-test-cases.js mindmaps/xx.mindmap.json
```

会检查：
- 字段完整性（步骤/预期/优先级/类型/层级）
- CASE-ID 唯一性（重复=ERROR）
- TCND 粒度（同条件超 4 条=WARN）
- P0 四问证据（影响/范围/恢复/决策）
- 标题中是否有实现词
- 空分组、重复标题、模板化步骤
- 文本乱码、截断、HTML 实体

有 ERROR 必须修复；WARN 逐条判断是否可接受。

## 五、研发自测建议

### 什么时候写用例

| 阶段 | 建议动作 |
|------|---------|
| 需求评审后 | AI 从 PRD 生成初稿，人确认测试条件边界 |
| 开发中 | 对自己负责的模块补充边界/异常用例 |
| 提测前 | 按 P0 → P1 顺序过一遍，标记 exec 状态 |
| QA 接手 | 导出 XMind/Markdown，或直接给 QA 打开脑图链接 |

### 自测完成定义

不是“全部用例跑完”，而是：

1. P0 全部通过。
2. 本次需求相关模块的 P1 全部通过或有明确风险接受。
3. 失败项有记录（exec=fail + 批注说明原因）。
4. 阻塞项写清被什么阻塞，是否需要环境修复。

### 交付给 QA 的标准

- 脑图结构清晰（一级=入口，二级=能力，叶子=用例）。
- 每条用例有 priority/expected/remark(CASE-* + 来源 + TCND-*)。
- 校验器输出 0 ERROR。
- P0/P1 备注含定级依据。
- 待确认项明确标出，不写成确定预期。

## 六、BYOS 实战数据

拿 BYOS V2.11.0 这份真实用例（175 条）举例：

| 指标 | 数值 |
|------|------|
| 一级分支 | 4 个（超管/管理端/APP/迁移工具） |
| 用例数 | 175 |
| e2e 用例 | 72（其中 59 条为真实跨系统业务流） |
| P0 | 35（20%） |
| P1 | 131（75%） |
| 追溯率 | 100% |
| 校验器结果 | 0 ERROR / 0 WARN（优化前） |
| 优化后 | 7 组重复 CASE-ID（ERROR）、6 个过粗 TCND（WARN） |

这说明：
- 分层和方法本身是够用的。
- 之前校验器没有强制 CASE-ID 唯一，导致追溯链有隐患。
- AI 生成 + 人工确认 + 确定性校验 三层组合，才能把用例资产维护住。

## 七、怎么开始

1. 本地启动：
   ```bash
   make dev
   ```
   打开 http://localhost:47213。

2. 新建一篇空白脑图或用“测试用例模板”。

3. 打开 AI 助手，把需求文档路径丢给它，让它先生成一版。

4. 自己过一遍：
   - 测试条件是否合理？
   - 优先级是否过高/过低？
   - expected 是否可判定？
   - 有没有缺“异常恢复”“数据一致性”？

5. 跑校验器，修复 ERROR，再看 WARN 是否需要处理。

6. 交付时把 `.mindmap.json` 给 QA，或导出 XMind。

---

## 八、一句话总结

**研发自测的本质不是“多跑几条用例”，而是把“要验证什么、依据什么判断、测到什么程度算完”提前想清楚。**

这个项目把这件事变成了可视化、可追溯、AI 可辅助的工作台，让研发和 QA 用同一套语言维护用例资产。

## 九、接入 test-platform 用例：历史测试面参考与影响分析

项目已经接入 TuriX 测试平台（`test-platform` MCP，地址 `http://172.16.200.10:3000/mcp`）。当开发新需求或修复缺陷时，平台的**历史用例是“测试面参考”，不是“直接修改对象”**——旧用例保持在平台不动，研发要做的是：

1. 从历史用例中识别**本次改动涉及的历史测试面**（哪些历史验证过的行为可能被破坏）。
2. 补齐历史没覆盖的**其他测试面**（数据一致性、幂等、权限、兼容……）。
3. 把两者写进脑图，作为本次自测和交付的回归范围。

### 1. 为什么要看历史测试面

历史用例沉淀了“这个功能过去验证过什么、踩过什么坑”。它们是免费的测试分析输入：

| 历史用例告诉你 | 怎么用 |
|---------------|--------|
| 历史验证过的行为 | 新改动是否破坏这些行为 → 生成回归测试点 |
| 历史踩过的坑（异常/边界用例） | 新改动是否引入同类风险 → 参考设计新用例 |
| 历史的数据/权限/兼容覆盖 | 新改动是否扩展了这些测试面 → 补充覆盖 |
| 历史用例的 P0/P1 分布 | 本次改动的回归重点 → 排自测优先级 |

### 2. 影响面清单

开发改动不是孤立的。一条需求的变更通常会影响：

| 影响面 | 要检查什么 | 去哪查 |
|--------|-----------|--------|
| **功能行为变化** | 历史用例的 expected 是否仍成立（是否需要回归） | 平台用例库（`search_version_test_cases`） |
| **接口契约变化** | 请求/响应字段、错误码、状态码是否变了 | 接口用例（`testLevel=api/contract`） |
| **数据模型变化** | 持久化断言、数据库用例是否受影响 | 数据层用例（`testLevel=database/service`） |
| **上下游依赖** | 依赖该模块的其他功能的用例是否受影响 | 平台用例库按模块搜索 |
| **兼容性承诺** | 旧客户端/旧版本数据的用例是否仍有效 | 兼容性用例（`caseType=compatibility`） |
| **权限/安全边界** | 新改动是否引入新的越权/隔离风险 | 安全用例（`caseType=security`） |

### 3. 推荐流程：四步法

#### 第一步：拉取相关历史用例（只读）

用 `test-platform` MCP 查询相关模块的已有用例（搜索工具是 `search_version_test_cases`，
按版本库过滤，返回树形摘要；查详情用 `get_version_test_case`）。**只查不改**：

```text
调用 search_version_test_cases，
project_id=<你的项目>，
library_version_id=<目标版本库>，
query="存储迁移"，
limit=50，
拿到模块下全部用例摘要，
再对关键用例调用 get_version_test_case 看步骤和预期详情。
```

关注点：
- 哪些用例的 `expected` 涉及本次改动的字段/状态/行为？
- 哪些用例属于同一业务链路的上游/下游？
- 哪些用例标记为 P0，一旦失效会阻塞发布？

#### 第二步：逐条判断影响类型（不改平台用例）

对每条相关历史用例，只做分类判断：

| 结论 | 脑图动作 | 平台动作 |
|------|---------|---------|
| **不受影响** | 脑图标注“无需回归 + 理由”。 | 不改。 |
| **历史行为被破坏** | 脑图建“回归测试点”，自测时重新执行。 | 旧用例不改；行为变化由需求/缺陷流程驱动平台侧维护。 |
| **历史覆盖缺失** | 脑图新增 `CASE-*`（remark 引用历史用例 ID 作来源）。 | 不改。 |

关键原则：**平台旧用例不直接修改**。研发把发现写进脑图（回归点/新用例），平台侧的用例维护由用例负责人按平台流程处理。

#### 第三步：补充其他测试面

按第 4 节测试面清单逐项检查：本次改动是否引入历史用例没覆盖的风险（数据一致性、幂等、并发、权限、兼容、性能、可观测、回滚）。缺哪个就在脑图补哪个。

#### 第四步：把影响范围写进脑图

在脑图里新建一个“回归影响”分支（或标记到现有用例），记录：

```text
受影响用例：CASE-XX-001、CASE-XX-002（来源：平台用例 ID）
影响原因：接口 XX 从字段 A 改为字段 B
需要执行的回归动作：重新执行受影响 P0/P1
不需要执行的理由：仅 UI 文案变化，不影响数据层
```

这样交付时 QA 能看到“你改了什么、影响了哪些历史用例、你自测覆盖到了没有”。

### 4. 其他测试面：分析时逐项评估，按方案决定补什么

下面是需求和技术方案分析时的思考清单。**不是每个需求都会涉及全部测试面**——先读技术方案，按最终实现方式判断哪些面被触发：被触发的面评估是否补充用例或检查表；不涉及的面不需要写用例。

判断依据是**实现方式**，不是需求文本有没有提到。例如：需求只说“支持取消任务”，但方案里实现了分片清理 → “数据一致性”适用；方案没有引入新配置项 → “配置/环境差异”不适用。

| 测试面 | 触发条件 | 自测动作 |
|--------|---------|---------|
| **数据一致性** | 涉及写操作/多表/外部存储 | 核对页面 + 接口 + 数据库 + 外部副作用 |
| **幂等/重复提交** | 有 POST/PUT/任务类操作 | 重复提交验证 |
| **并发/竞态** | 多人操作同一资源 | 并发操作验证 |
| **权限边界** | 涉及角色/权限/租户隔离 | 越权访问验证 |
| **兼容性** | 涉及协议/客户端版本/数据迁移 | 旧版本行为验证 |
| **性能基线** | 涉及批量/大文件/高频操作 | 容量边界验证 |
| **可观测性** | 涉及新逻辑/新错误路径 | 日志/审计/trace 验证 |
| **回滚/降级** | 涉及开关/配置/迁移 | 回滚路径验证 |

被触发的面不一定要每条都写成正式用例——风险高的写用例，轻量的建“自测检查表”节点打钩；未触发的面不写。

### 5. 一个实际例子

假设需求是“BYOS 迁移任务的取消行为从‘暂停’改为‘真正取消’”：

**新用例**（写进脑图，CASE-ID 从 TCND 生成）：
```text
迁移执行中取消任务，已复制分片不再继续且任务状态变为已取消
```

**平台历史用例检查**（用 `search_version_test_cases` 查“迁移任务”）：
- CASE-PLATFORM-101：“迁移暂停后恢复任务，已完成项不重复执行” → **回归**：取消语义变化后，暂停/恢复是否仍按原预期？
- CASE-PLATFORM-102：“迁移完成后切换存储” → **不受影响**（成功路径不变）。
- CASE-PLATFORM-103：“重复确认同一次迁移，不重复复制” → **可能受影响**：取消后的重复确认语义变了。

**脑图“回归影响”节点**：
```text
变更影响：
- CASE-PLATFORM-101：取消语义变化后回归验证暂停/恢复行为（脑图新增回归用例）
- CASE-PLATFORM-102：不受影响，无需回归
- CASE-PLATFORM-103：需新增“取消后重复确认”用例
其他测试面：数据一致性（已复制分片是否清理）、幂等（重复取消）、审计（取消事件记录）
```

### 6. 落地建议

1. **平台旧用例是只读参考**：历史测试面靠它识别，修改由平台流程驱动；脑图负责设计、拆分和自测记录。
2. **用 MCP 把两个工具串起来**：`test-platform` 只读查询历史用例，`ai-mind-map` 管理设计和自测，AI 协调两者。
3. **每次变更必须回答三个问题**：
   - 哪些历史测试面受影响？（search_version_test_cases）
   - 需要新增什么？（脑图 + TCND + CASE）
   - 需要跑哪些回归？（脑图里标记 exec 状态）
4. **交付时给脑图**：设计 + 自测记录 + 回归范围 + 其他测试面检查结果，QA 据此接管。
