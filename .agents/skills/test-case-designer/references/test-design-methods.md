# 测试设计方法选择

先判断“哪些方法适用”，再生成用例；不要每个需求都机械套满正常/异常/边界/安全/性能。

## 一、按被测对象选择方法

| 被测对象/风险 | 首选方法 | 关键检查点 | 常见错误 |
|---|---|---|---|
| 状态流转（审批、发布、上下架、开通、异步任务） | **状态机** | 合法与非法转换、重复事件、并发事件、回滚、半完成状态 | 只测首尾状态，遗漏中间态和取消态 |
| 完整用户业务链路 | **场景法 / 端到端流程** | 主成功流、分支流、异常中断、恢复 | 拆成接口碎片，无法验证业务闭环 |
| 字段、大小、数量、超时、分页 | **等价类 + 边界值** | 有效/无效等价类、上下边界、空值、超长、临界并发 | 只测 0/1/最大值，漏边界内外 |
| 权限、资格、版本、开关组合 | **判定表 / 决策表** | 条件组合、互斥、默认、越权 | 只测两两组合，漏关键越权组合 |
| 网络、进程、数据库或外部依赖异常 | **故障注入** | 超时、断开、部分失败、重试、幂等、恢复 | 只测“报错提示”，不测数据是否一致 |
| 客户端/服务端版本、数据创建阶段 | **兼容性矩阵** | 旧客户端×新服务端、新×旧、跨版本数据 | 只改名称，用例内容完全相同 |
| 同一事实存在多个副本或外部副作用 | **数据一致性核对** | 权威记录、派生记录、外部结果；提交、删除、回滚后对账 | 只看页面，不核对持久化结果和外部副作用 |
| 租户、凭证、URL、日志 | **安全测试** | 跨租户访问、越权、凭证泄露、日志脱敏、签名/有效期 | 只测未登录 401，漏水平/垂直越权 |
| 大数据、并发、批处理和资源占用 | **性能测试** | 容量边界、并发数、延迟分位数、内存/句柄、失败恢复 | 只测单请求，不测批量和长稳 |
| 低频防御/隐藏接口 | **错误推测 + 接口级防御** | 重复调用、极端参数、页面无入口的防御逻辑 | 把探索性场景标成 P0 |
| 三个以上相对独立的条件维度 | **Pairwise / 组合测试** | 每个重要取值对至少出现一次，高风险组合单独补充 | 生成全部笛卡尔积或把 Pairwise 当完整风险覆盖 |
| 规则不完整、历史问题多或需要发现未知风险 | **探索式测试 / 检查表** | 明确章程、时间盒、观察记录和后续沉淀 | 只写“自由探索”，没有目标和证据 |
| 输出难以直接给出唯一正确答案 | **不变量 / 蜕变测试** | 输入变换关系、结果应保持或同步变化的性质 | 把当前实现结果当作唯一正确答案 |
| 算法、复杂分支或安全关键代码 | **白盒覆盖（按需）** | 语句、分支、条件、异常路径和不可达路径 | 手工 UI 用例强行覆盖代码结构 |

## 二、先判断适用性

对每个需求快速回答：

1. 是否存在**状态**或生命周期？→ 状态机。
2. 是否是**用户完整业务链路**？→ 场景法 + 端到端。
3. 是否有**输入范围/容量/时间**？→ 等价类/边界值。
4. 是否有**多条件组合/权限矩阵**？→ 判定表。
5. 是否依赖**外部资源或可失败组件**？→ 故障注入。
6. 是否存在**多版本/多阶段数据**？→ 兼容矩阵。
7. 是否存在**多个权威或派生数据结果**？→ 数据一致性核对。
8. 是否涉及**租户/凭证/敏感信息**？→ 安全测试。
9. 是否有**容量/并发/批量**目标？→ 性能测试。
10. 是否有三个以上独立条件维度且全排列过大？→ Pairwise，并单独补高风险组合。
11. 是否缺少完整规则或需要发现未知风险？→ 探索式测试 / 检查表。
12. 是否难以直接判断唯一正确输出？→ 不变量或蜕变测试。
13. 是否需要从代码结构证明覆盖？→ 白盒覆盖；仅在能观察或插桩的测试层级使用。

只选适用的方法；方法覆盖要能解释“为什么不用其余方法”。

## 三、覆盖组合原则

- 正常流、异常流、状态转换、数据一致性是**基础覆盖**，不能只做页面检查。
- 优先级不按方法机械分配：安全/数据用例只有涉及越权、敏感信息、数据损坏、跨租户隔离才升 P0。
- 条件间存在明确业务规则时优先使用判定表；条件相对独立且三维以上时可用 Pairwise。高风险、历史缺陷和禁止组合必须显式加入，不能依赖自动组合偶然覆盖。
- 同一风险点可由多个共同断言证明，但互不依赖、修复责任不同的风险应拆成独立用例。
- 版本、运行环境、输入类型等交叉维度优先放标题或标签，不增加目录层。

## 四、测试层级与测试类型

测试层级回答“从哪里验证”，测试类型回答“验证哪类质量风险”，两者不能混用：

- 测试层级：UI、API、服务、数据库、契约、端到端。
- 测试类型：功能、边界、异常、安全、性能、兼容、数据、工作流等。

使用 `props.testLevel` 记录层级，不要将 UI/API 等层级值塞入 `caseType`。若同一行为可在更低层级稳定、快速地验证，优先在低层验证；端到端只保留跨边界核心链路。

## 五、非功能方法选择

只有存在事实依据或明确风险时才设计非功能用例：

- 性能：容量、负载模型、持续时间、延迟分位数、吞吐或资源阈值。
- 可靠性：故障窗口、恢复目标、重试/幂等、数据丢失容忍度。
- 安全：身份、授权、租户隔离、敏感数据、审计和凭证生命周期。
- 兼容性：受支持版本、平台、协议或数据代际矩阵。
- 可访问性：适用标准、键盘路径、焦点、语义和对比度。
- 国际化：语言、时区、地区格式、字符集和文本扩展。

没有量化目标或契约时，先标记待确认，不写“性能良好”“满足无障碍要求”等不可判定预期。

## 六、覆盖度自检

- [ ] 每条核心链路都有成功流 + 主要异常/恢复路径。
- [ ] 状态机覆盖合法与非法转换、重复事件、取消或回滚、半完成状态。
- [ ] 边界值覆盖上下边界内外、空值、超长、临界并发。
- [ ] 判定表覆盖关键权限/版本/开关组合与越权。
- [ ] 故障注入后核对数据一致性，而不只是提示文案。
- [ ] 兼容矩阵覆盖关键版本或运行环境组合，且用例内容确有差异。
- [ ] 数据一致性用例写清权威数据源、派生结果和外部副作用。
- [ ] 安全用例覆盖水平/垂直越权、跨租户、凭证与日志。
- [ ] 性能用例给出容量/并发/阈值，而不是“性能正常”。
- [ ] 没有把仅接口可触发、页面无入口的防御场景过度升级为 P0。
- [ ] 三维以上组合已说明采用全组合、判定表、Pairwise 或代表性抽样的原因。
- [ ] 探索式测试有章程、时间盒和记录方式；发现的稳定风险已沉淀为可回归用例。
- [ ] 测试层级与测试类型没有混用，端到端用例没有重复低层可稳定验证的全部细节。
- [ ] 适用的非功能用例包含明确标准或量化阈值。
