# 用例优先级标准（P0–P3）

优先级描述的是**该用例失败对发布与业务的风险**，不是开发工作量，也不是缺陷严重程度本身。

## 等级定义

| 优先级 | 定义 | 典型用例 | 执行要求 |
|---|---|---|---|
| **P0** | 失败会阻塞发布，且没有可接受的临时绕行、降级或风险接受方案 | 核心交易完全不可用、不可恢复的数据损坏、严重越权或关键隔离失效 | 每次发布必须执行，失败即停止发布 |
| **P1** | 高业务风险或高发生概率，通常需要修复；若发布，必须有负责人明确接受风险并给出缓解或绕行方案 | 主要功能受损、可恢复的数据不一致、关键兼容链路、主要异常恢复 | 完整回归必须执行；失败需修复或显式风险接受 |
| **P2** | 次要功能、低概率边界、影响范围有限 | 表单校验、状态刷新、非关键筛选、提示信息、低频兼容组合 | 常规回归执行，按风险决定是否阻塞 |
| **P3** | 极低概率、低影响、探索性或页面无法直接触发的防御性场景 | 重复调用隐藏接口、轻微展示问题、非关键审计补充、极端输入组合、长期稳定性探索 | 定向或周期性执行，通常不阻塞发布 |

## 判断维度

对每条用例依次评估：

1. **业务影响**：失败时哪些用户/业务不可用？是否核心收入或合规链路？
2. **发生概率**：正常操作是否会触发？还是极端输入/隐藏接口？
3. **可恢复性**：能否重试、回滚、人工修复？是否存在数据不可逆损坏？
4. **数据与安全风险**：是否涉及越权、跨租户隔离、敏感信息、数据一致性？
5. **版本核心目标**：是否属于本次发布明确承诺、必须保证的能力？

结论 = 风险等级，不是“测试类型”。正常/异常/安全/接口用例都可能落在任意优先级。

## 定级规则

- 不允许默认全部生成 P0；同一分组可以因实际风险全部为 P0，但每条都必须有独立的阻断理由。
- 安全或数据用例只有涉及**严重越权、敏感信息泄露、数据损坏或关键隔离失效**时才提升为 P0。
- 页面没有操作入口、只能通过接口模拟的防御性场景，通常是 P2/P3。
- 仅 UI 展示、低频兼容组合、提示文案类问题，不应标 P0。
- **P0 必须能回答**：“该用例失败是否禁止发布？”回答不了就不是 P0。
- “禁止发布”是判断结果，不是定级依据。仅写“核心链路”“失败禁止发布”或“发布承诺”不能单独支持 P0。
- 同一业务风险只保留能证明发布承诺的最小 P0 集合。实现层、接口层、页面层或多个兼容组合若验证的是同一个失败影响，不得全部重复标为 P0。
- **P0/P1 必须**具备完整、可直接执行的步骤和明确断言，不能只写概念性检查。
- 无法确认时标记“待确认”，并记录可能影响定级的缺失事实；不要通过机械上调优先级掩盖信息不足。
- 用例范围或风险变化时允许重新定级；重新定级要同步更新 `remark`。

## 备注中的定级依据

P0/P1 的 `remark` 必须包含失败影响或定级理由。P0 至少回答以下四项：

1. **影响**：具体损失是什么（不可用、数据损坏、越权或泄露）。
2. **范围**：影响单个用户、单个租户、全部租户还是升级存量。
3. **恢复**：是否可重试、回滚、降级、人工修复或使用旧链路绕行。
4. **决策**：为什么当前版本不能接受该风险，而不是笼统写“禁止发布”。

建议格式：

```text
CASE-012 · 来源：需求 §3.2 / 设计说明 §4；定级：P0；影响：迁移对象损坏；范围：全部升级存量；恢复：切换后无法通过重试或回滚恢复；决策：本次版本以存量无损升级为发布承诺
```

若无法填完整四项，通常应先定为 P1 或标记“待确认”，而不是先升为 P0。

## P0 四问门禁

只有四问均为“是”时才定为 P0：

1. 失败是否直接破坏本次版本的核心发布承诺，或造成严重安全/不可恢复数据风险？
2. 影响是否达到关键用户群、租户隔离边界或核心存量，而非单一低频展示/边界？
3. 是否不存在可接受的重试、回滚、降级、人工修复或旧链路绕行？
4. 发布负责人是否会仅因这一条失败而停止本次发布？

任一答案为“否”：根据影响定为 P1/P2/P3。任一答案为“未知”：标记待确认，不得用 P0 掩盖信息不足。

## 分布检查不是定级规则

P0/P1 的数量和比例只用于发现异常分布，不能反向决定单条用例的优先级。默认在 P0 超过 35% 时触发复核；这不是要求把比例压到 35%，而是要求逐条提供四问证据。小型、低风险或专项用例集可能没有 P0；高风险专项也可能在复核后保留较高 P0 占比。

## 质量门禁（优先级相关）

发布/评审前逐条确认：

- [ ] 是否存在大量无独立阻断理由的 P0？
- [ ] 每条 P0 是否通过“影响、范围、恢复、决策”四问？
- [ ] 同一风险是否被不同层级或兼容组合重复标为多个 P0？
- [ ] 若范围包含核心主链路，是否有相应 P0？
- [ ] 数据一致性、租户隔离、不可逆操作是否被低估？
- [ ] 仅展示或低频防御场景是否被错误标成 P0？
- [ ] 每条 P0/P1 是否明确说明失败影响？
- [ ] 优先级是否与发布门禁、回归执行范围一致？
- [ ] P0/P1 是否都有可执行步骤与可判定预期？
- [ ] 优先级分布是否与本次范围、风险和执行策略一致？

`scripts/validate-test-cases.js` 会检查 P0/P1 字段完整性和定级说明；P0 占比、无 P0、无 P1和全 P0 分组属于可配置的分布提示，默认不作为正确性门禁。

## 常见误判

| 误判 | 为什么错 | 正确做法 |
|---|---|---|
| “正常流都是 P0” | 正常流里也有次要功能 | 看业务影响与版本目标 |
| “异常/安全一律 P1/P0” | 低概率防御场景可能只是 P2/P3 | 看越权/数据/概率 |
| “边界值都是 P2” | 关键容量边界也可能阻断核心业务 | 看是否影响核心链路或造成不可恢复结果 |
| “接口用例技术性强所以 P0” | 技术实现不等于业务风险 | 用业务影响判断 |
| “先全标 P0，后面再降” | 发布门禁失真，回归无法收敛 | 设计时即按风险定级 |
