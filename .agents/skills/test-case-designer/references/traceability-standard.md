# 测试追溯与覆盖标准

追溯的目标是回答两个问题：每条重要事实由哪些用例验证？每条用例为什么存在？脑图层级只负责导航，不能替代追溯关系。

## 最小追溯链

```text
事实来源 → 测试条件 → 用例 ID
```

- **事实来源**：需求条目、验收条件、接口契约、状态规则、数据约束、历史缺陷或已确认风险。
- **测试条件**：`TCND-*`，描述一个可独立验证的行为或风险；不要把它当成模块名。
  同一 `TCND-*` 下多条用例必须存在输入、状态、层级或判定点差异；超过 4 条时会触发“条件过粗”告警。
- **用例 ID**：稳定的 `CASE-*`；修改标题或移动目录时不得随意更换，且**全文档必须唯一**。
  同一个 `CASE-*` 复用到不同用例会直接破坏追溯链，校验器会判为 ERROR。

## 用例记录方式

每条用例的 `remark` 至少记录：

```text
CASE-<编号> · 来源：<可定位引用> · 测试条件：TCND-<编号>
```

P0/P1 再补充失败影响或发布决策依据。接口名、内部状态码和代码路径可继续放在备注中，但不能替代业务来源。

当前协议使用独立的 `testLevel` 表达测试层级；来源和测试条件暂存在 `remark`。不要把 UI/API 等层级值塞入 `caseType`。

## 覆盖检查

输出前至少检查：

1. 每条范围内的高风险来源都有测试条件。
2. 每个已确认测试条件至少被一条用例覆盖。
3. 每条用例至少关联一个来源和测试条件。
4. 同一测试条件被多条用例覆盖时，各用例的输入、状态、层级或判定点确有差异。
5. 待确认和范围外测试条件不被误报为已覆盖。
6. `CASE-*` 在全文档内没有重复；同一 `TCND-*` 下用例数超过 4 条时，逐条确认它们不是同一模块下的批量复制，必要时应拆分更细测试条件。

覆盖状态使用：

- **已覆盖**：有可执行、可判定的用例。
- **部分覆盖**：只覆盖部分状态、组合或测试层级。
- **未覆盖**：范围内但没有对应用例。
- **待确认**：缺少事实或测试预言，暂不能设计确定性用例。
- **范围外**：已明确不属于本次任务，并记录理由。

## 变更影响与增量维护

需求或契约变化时：

1. 找到受影响的事实来源和测试条件。
2. 定位关联用例，判断更新、保留、废弃或新增。
3. 保留未受影响用例及其稳定 ID。
4. 不再适用的用例先标记废弃并说明替代关系；未经授权不物理删除。
5. 报告变更前后覆盖差异和仍未覆盖的风险。

## 完成判定

不是以用例数量作为完成标准，而是同时满足：

- 范围内的事实来源已有明确处理结论。
- 高风险测试条件完整覆盖。
- 中低风险测试条件达到约定的代表性覆盖。
- 没有无来源用例。
- 未覆盖、待确认和范围外内容已显式报告。
