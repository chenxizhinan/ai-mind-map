# 用例书写标准

适用节点类型：`case`（叶子用例）。每条用例必须能被执行、被判定、被追溯。

## 必填字段

| 字段 | 要求 |
|---|---|
| `text`（标题） | 一个主要测试目标；体现“条件 + 动作 + 主要结果” |
| `props.precondition` | 执行前必须成立的状态；确实没有时写“无”，不能空着不思考 |
| `props.steps` | 有序、可执行的步骤（数组）；禁止“执行对应操作”这类模板话 |
| `props.expected` | 可观察、可判定的结果；禁止“功能正常/符合预期” |
| `props.priority` | `P0`–`P3`，按 `priority-standard.md` |
| `props.caseType` | 测试类型：`functional` / `boundary` / `exception` / `security` / `performance` / `compatibility` / `data` / `workflow` / `reliability` / `accessibility` / `localization` |
| `props.testLevel` | 测试层级：`ui` / `api` / `service` / `database` / `contract` / `e2e` |
| `props.remark` | 稳定用例 ID + 来源 + 测试条件 ID；必要时补充定级理由和技术依据 |

建议补充：
- `props.detail`（folder/普通节点）：长背景、数据清单、参考材料，保持标题简短。
- `remark` 中记录“待确认”项，禁止把猜测写成预期。

## 标题格式

```text
必要条件下执行动作，主要结果
```

- 标题要让不了解实现的人一眼看懂测试意图：处于什么业务状态、执行什么动作、最主要的结果是什么。
- 标题只表达一个主要测试目标；不要把互不依赖、可分别通过或失败的目标塞进一条用例。
- 条件写业务状态，不写实现细节；动作写用户/系统可执行的动作；结果写可观察现象。
- 父级已经表达的业务域不要在每条标题中重复，例如父级是某类资源时，子用例无需再次加同名方括号前缀。
- 长度以一眼可读为准（最多 100 个字符），技术参数、多项断言和数据清单放进步骤、预期或详情。
- 标题必须是完整原文，不能包含复制自界面的截断尾缀 `…` / `...`；过长时应人工改写并把细节移入详情，不能直接截断。

示例：

```text
未登录时提交受保护操作，跳转登录页且不产生业务数据
任务处理中暂停后恢复，已完成项不重复执行
达到容量上限后继续新增记录，系统拒绝提交并保留原数据
```

不合格：

```text
上传功能测试                       # 无动作/无结果
验证 INTERNAL_PENDING 状态下 internal_record 更新   # 内部实现词
登录成功                           # 缺动作
检查功能正常                       # 预期不可判定
【多个条件】A 正常、B 报错、C 超时     # 一条用例多个测试点
```

## 步骤与预期

- 步骤必须是**可执行动作**：输入/点击/调用/等待/切换/构造数据……
- 每步不超过两句话；一步一个动作；必要时写清数据与入口。
- `expected` 是整条用例的通过条件，不要求与步骤数组机械一一对应。存在多个必要断言时按 `1. ...；2. ...` 编号，且这些断言必须共同证明同一主要测试目标。
- 预期写“看得到/查得到”的现象：页面跳转、提示文案、返回码、数据状态、文件是否存在。
- 数据一致性类用例要明确需要核对的权威数据、派生数据和外部副作用。
- 接口路径、内部状态码、Reference 编号、实现名放 `remark` 或技术步骤。若响应字段或错误码本身就是契约断言，可以写入预期，但要同时说明其业务含义。

## 详情与备注的分工

| 内容 | 放哪里 |
|---|---|
| 长背景、数据清单、参考材料、链接 | `props.detail`（folder）或独立的准备工作节点 |
| 来源、Reference 编号、接口名、内部状态码、实现说明 | `props.remark` |
| 标题应保持简短、可直接阅读 | `text` |

## 独立性与可执行性

- 一条用例只验证一个主要测试目标；允许页面、接口、数据和外部副作用等多个断言共同证明该目标。
- 如果某个断言可能单独失败且对应不同风险、不同修复责任或不同执行条件，应拆成独立用例。
- 前置状态必须可构造；如果只能靠“假设已处于某状态”而无法准备，标注“待确认/需要测试数据支持”。
- 不写“执行对应操作”“按需求验证”等无法执行的描述。
- 不写“功能正常”“无异常”“符合预期”等无法判定的预期。

## 业务语言与实现信息

标题和目录必须使用执行者可理解、可观察的业务语言，不用内部实现名代替业务状态或结果。以下内容不得出现在标题中：

- 接口路径、HTTP 方法、状态码和 Header 名。
- 数据库字段、JSON 字段、枚举常量、权限标识和表名。
- 内部模型、状态容器、技术组件和协议术语，包括单个英文专业词；应改写成业务含义。
- snake_case、kebab-case、代码常量或其他明显的标识符形式。

确需验证对外契约、数据库约束或机器可读错误时，在技术步骤、预期或 `remark` 写入原始标识，并同时说明其业务含义。产品名称和面向用户公开的标准名称可保留，但不得借此把实现细节塞回标题。

## 事实来源与禁止臆测

- 写之前确认需求/RFC/接口/代码中的行为；区分已实现、计划实现、待确认。
- 无法确认的行为不得写成确定预期；标记“待确认”并说明缺失的信息来源。
- 每条用例的 `remark` 保留稳定用例 ID、可定位来源和测试条件 ID，格式遵循 `traceability-standard.md`。

## 文本完整性

- 写入和最终 Review 后检查全部文本字段：标题、详情、前置条件、步骤、预期和备注。
- 禁止出现 Unicode 替换字符 `�`、常见错误编码片段、未解码 HTML 实体或复制自页面的截断文本。
- 发现乱码时回到事实来源恢复原文；无法确认原文时标记“待确认”，不得凭上下文猜测后静默覆盖。
- MCP 批量写入后必须重新读取文档并运行校验器，不能只检查写入请求是否成功。

## 自查清单

- [ ] 标题只有一个主要测试目标，且包含条件/动作/主要结果。
- [ ] 单看标题即可理解测试意图，不依赖父级名称、详情或内部实现词。
- [ ] 前置条件明确（或明确为“无”）。
- [ ] 步骤可执行，没有模板化描述。
- [ ] 预期可观察、可判定，没有“功能正常”。
- [ ] 优先级与失败影响一致（P0/P1 尤其）。
- [ ] 内部实现词只出现在备注/技术步骤中。
- [ ] 来源已写入 remark；待确认项已标注。
- [ ] 全部文本字段无乱码、未解码实体和截断内容。
