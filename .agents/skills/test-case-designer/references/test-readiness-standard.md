# 测试准备区标准（测试输入 / 范围 / 环境 / 数据）

目标：让用例脑图不只是用例清单，而是一份**拿到就能执行**的完整测试交付物。
整理脑图时，必须同时整理让用例可执行的测试资料，统一放在文档顶层的
「00 测试准备」分区——这是唯一允许存在的非用例固定分区，命名固定为
`00 测试准备`，置于全部功能分支之前，便于一眼定位。

## 固定结构

```text
00 测试准备（folder）
├── 测试输入（需求与设计来源）（folder）
│   └── 每项来源一个节点：标题 = 名称，props.remark = 需求编号 / 文档链接
├── 测试范围（folder）
│   ├── 范围内（folder）→ 子节点 = 本次覆盖的模块 / 链路（与用例一级分支一一对应）
│   └── 范围外（folder）→ 明确不做的内容与原因
├── 测试环境准备（folder）
│   ├── 环境与版本（folder）→ 环境地址、部署版本、配置项、功能开关
│   ├── 账号与权限（folder）→ 各角色测试账号、租户、授权状态
│   └── 依赖服务（folder）→ 依赖系统 / mock / 联调方与联系人
└── 测试数据准备（folder）
    ├── 基础数据（folder）→ 前置数据、字典、初始状态
    └── 专项数据（folder）→ 边界数据、大数据量、异常数据、数据清理方式
```

可根据项目增删三级节点（如新增“准入 / 准出标准”“风险与依赖”），但前四项
（测试输入、测试范围、测试环境准备、测试数据准备）不可缺省。

## 内容要求

- 每个叶节点标题 = 可核对的具体事项（如“预发环境 https://… 版本 v2.3”、“租户 A 管理员账号 ×2”）。
  禁止“详见文档”“待补充”这类无信息占位；确实未就绪的写明缺口与负责人（props.note）。
- 长文本（环境搭建步骤、数据清单、链接列表）放 `props.detail`，标题保持一行可读。
- 测试范围内的模块名必须与用例树一级分支一一对应；用例树出现范围外模块时，
  要么在范围内补说明，要么在范围外节点说明原因。
- 测试输入节点必须带来源（props.remark = 需求编号 / 文档链接），与用例的追溯来源一致。
- 环境与数据准备要和用例的 props.precondition 呼应：前置条件里出现的账号 / 数据，
  应能在准备区找到来源。

## 何时创建与维护

- **新建设计**：create_document 后、写用例前，先创建「00 测试准备」完整骨架并填充已知项；未知项标“待确认”。
- **增量补充**：文档缺失准备区时主动补建骨架并填充已知信息；已存在时只同步变化项，不重复创建。
- **层级重组**：不新建，但核对准备区与用例树的一致性（范围 ↔ 一级分支、数据 ↔ 前置条件）。
- **只读评审**：检查准备区完整度并在报告中指出缺口，不写入。

## 反例

- 「测试数据准备」下只有一句“详见测试计划”——没有可核对的清单。
- 环境准备只有“测试环境”一个空文件夹，没有任何地址 / 版本 / 账号。
- 范围内节点列了 5 个模块，但用例树只有 3 个一级分支，多出的模块没有解释。
- 把大段环境配置塞进节点标题，而不是 props.detail。
- 用例的 precondition 写“使用租户 A 管理员账号”，但准备区找不到这个账号的任何说明。
