# 测试分析标准

测试分析回答“需要验证什么、为什么验证、依据什么判断”，用例设计回答“如何执行验证”。除纯文字修订外，先完成测试分析再新增或重写用例。

## 最小分析结果

至少形成以下内容，可保留在工作记录中，也可在范围较大时先展示给用户：

| 项目 | 必须回答的问题 |
|---|---|
| 测试对象 | 哪个产品入口、角色、接口、后台流程或数据能力被改变？ |
| 事实来源 | 哪些需求、验收条件、契约、设计、代码或缺陷构成判定依据？ |
| 范围 | 本次覆盖什么、不覆盖什么，哪些内容仅做回归？ |
| 测试层级 | 主要从 UI、API、服务、数据、契约还是端到端验证？ |
| 状态与条件 | 有哪些前置状态、角色、配置、版本、输入和依赖组合？ |
| 测试条件 | 哪些行为或风险必须被独立验证？ |
| 测试预言 | 每个测试条件依据什么事实判定通过或失败？ |
| 风险 | 失败影响、发生概率、可恢复性、数据/安全影响是什么？ |
| 环境与数据 | 需要哪些账号、权限、数据、外部依赖和可观测手段？ |
| 待确认项 | 哪些行为缺少依据，谁或什么资料可以确认？ |

## 提取测试条件

测试条件是可由一个或一组用例证明的行为或风险，不是操作步骤。按以下顺序提取：

1. 从每条可验证需求、验收条件和契约中提取承诺行为。
2. 从状态模型中提取合法转换、非法转换、重复事件、中断和恢复。
3. 从输入约束中提取有效类、无效类和边界。
4. 从角色、权限、版本、配置和依赖中提取会改变结果的条件。
5. 从持久化事实和外部副作用中提取一致性、幂等与补偿要求。
6. 从历史缺陷和高风险假设中提取回归条件。
7. 从测试平台历史用例中提取历史测试面（若有 test-platform MCP 接入）：
   - 用 `search_version_test_cases` 按模块/关键词只读查询历史用例摘要；
   - 对关键用例用 `get_version_test_case` 看步骤与预期详情；
   - 识别三类信息：历史验证过的行为（回归点）、历史踩过的坑（同类风险）、历史覆盖缺口（其他测试面）；
   - **平台旧用例不直接修改**，发现问题写进测试分析，用例产出落在脑图并引用平台用例 ID 作来源。

每个测试条件应包含：

```text
条件 ID：TCND-<稳定编号>
行为/风险：一句话描述需要证明的事实
来源：需求、验收条件、契约或实现证据
判定依据：可观察结果或数据不变量
风险等级：高 / 中 / 低，并说明原因
适用方法：状态机、边界值、判定表、场景法等
状态：已确认 / 待确认 / 范围外
```

## 测试预言

测试预言必须来自事实源或稳定不变量，优先级如下：

1. 明确的验收条件、协议或对外契约。
2. 当前有效的 Reference、状态模型或数据约束。
3. 已确认的产品行为和兼容承诺。
4. 经确认的历史基线。

不得仅以“当前实现就是这样”作为预言，也不得从界面现象反推未声明的产品规则。无法确认时写“待确认”，说明缺失的判定来源。

对于结果不易直接判断的对象，可使用：

- 不变量：总量守恒、唯一性、单调性、权限隔离、幂等。
- 对照：同一输入在已知可信实现或前后版本的结果差异。
- 蜕变关系：输入按已知关系变化后，输出应保持或按相同关系变化。
- 多点观测：同时核对页面、接口、持久化数据和外部副作用。

## 风险驱动的覆盖深度

- **高风险**：覆盖主流程、主要分支、失败恢复、权限/数据边界和关键组合；判定依据必须明确。
- **中风险**：覆盖代表性正常、异常和边界组合；避免无价值的全排列。
- **低风险**：选择代表性样本，必要时使用检查表或探索式测试；不要为了数量复制用例。

风险决定覆盖强度，不直接等同于用例优先级。优先级还受发布范围和执行策略影响。

## 变更影响面清单（分析时逐项评估，按方案决定取舍）

以下测试面**不是每个需求都会涉及**。它们是需求分析和技术方案评审时的**思考清单**：先读需求与技术方案，判断本次实现是否触发某个测试面的触发条件；由 AI/设计者**基于最终实现方案判断是否适用**——适用的面评估是否需要补充测试用例或检查表节点；不涉及的面不需要写用例，也不强制在脑图里留“不适用”节点（除非用户明确要求留痕）。

| 测试面 | 触发条件 | 自测动作 |
|--------|---------|---------|
| 数据一致性 | 写操作/多表/外部存储 | 核对页面 + 接口 + 数据库 + 外部副作用 |
| 幂等/重复提交 | POST/PUT/任务类操作 | 重复提交验证 |
| 并发/竞态 | 多人操作同一资源 | 并发操作验证 |
| 权限边界 | 角色/权限/租户隔离 | 越权访问验证 |
| 兼容性 | 协议/客户端版本/数据迁移 | 旧版本行为验证 |
| 性能基线 | 批量/大文件/高频操作 | 容量边界验证 |
| 可观测性 | 新逻辑/新错误路径 | 日志/审计/trace 验证 |
| 回滚/降级 | 开关/配置/迁移 | 回滚路径验证 |
| 配置/环境差异 | 配置项/环境变量/多环境 | 各环境配置组合验证 |
| 任务调度/定时 | 定时任务/重试/延迟队列 | 触发时间、重复调度、错过窗口行为验证 |
| 数据生命周期 | 数据保留/归档/清理 | 过期数据行为、归档一致性验证 |
| 存储容量/配额 | 存储空间/配额限制 | 配额边界、超配额行为验证 |
| 升级/迁移 | 版本升级/数据迁移/灰度 | 升级路径、回退、灰度验证 |
| 消息/事件 | 消息推送/事件通知/回调 | 送达、重复、乱序、失败重试验证 |
| 时间相关 | 时区/定时/超时/有效期 | 时区边界、时钟偏移、到期行为验证 |
| 资源回收 | 临时资源/连接/句柄释放 | 异常后资源是否泄漏验证 |
| 审计/合规 | 操作记录/敏感数据/权限变更 | 审计完整性、脱敏、留存验证 |

判断依据 = **技术方案的实现方式**，不是需求文档有没有提到。例如：需求只说“支持取消任务”，方案里实现了分片清理 → “数据一致性”适用；方案没有引入新配置项 → “配置/环境差异”不适用。

## 何时先停下来确认

以下情况先输出分析摘要和待确认项，不直接生成确定性预期：

- 事实来源互相冲突，或实现与已批准设计不一致。
- 关键状态、错误处理、兼容承诺或数据权威来源缺失。
- 多种层级划分会明显改变执行方式，且无法从目标读者判断。
- 用户要求的范围会造成大量组合，但没有风险或代表性选择依据。

普通、范围清晰的小改动不需要额外审批步骤，可完成分析后直接设计并校验用例。
