# 用例层级标准

目标：每个文件夹层只回答一个分类问题，让读者能够沿着稳定、可理解的路径找到用例，而不是按测试方法或内部实现模块堆目录。

## 决策顺序

先选择**第一主轴**，再按需要选择**第二主轴**，不要默认复制固定层级：

1. 谁按照什么入口执行：产品区域、使用角色、客户端或管理端。
2. 哪个稳定业务能力或用户任务：创建、审批、发布、查询、恢复等。
3. 哪个条件最显著地改变预期结果：生命周期状态、版本、权限、配置或数据阶段。
4. 叶子节点为具体用例（`case`）。

优先选择最符合执行和查找习惯的维度作为第一主轴。例如以页面区域执行时按产品入口分组；以状态迁移回归时按生命周期分组；以 API 契约验收时可按稳定资源能力分组。

除此之外，不要继续为数据类型、实现方案、输入类别或接口名单独增加目录；交叉维度优先放进用例标题、标签、`props.detail` 或 `props.remark`。

## 硬性规则

- 同一层只表达一个分类维度，禁止“产品 + 测试方法 + 模块”混在同一层。
- 默认控制在 **2–4 层文件夹**。超过 4 层时必须能说明额外层级如何提高执行或查找效率；校验器只提醒，不把层数作为绝对错误。
- 目录名必须使用目标读者能够理解的业务语言；接口路径、字段名、枚举值、表名和内部组件名不得作为业务目录。
- 一条用例只能挂在一个叶子测试点下；不要为了“方便检索”重复挂载。
- 业务分组若没有任何后代用例，应补齐或删除。明确标记为测试资料、准备工作或参考说明，且 `detail` 中有有效内容的辅助节点可以没有后代用例。
- 已有脑图重组时，保留原有业务含义，不做“按测试方法重新分目录”的机械重排。

## 通用示例

```text
用户端
├── 当前版本
│   ├── 初始状态
│   ├── 处理中
│   └── 失败后恢复
└── 兼容版本
```

输入类型、数据格式和实现差异属于交叉维度，通常放在标题、标签或追溯信息中。树是导航结构，不是完整覆盖模型。

```text
【兼容版本｜已完成】提交大文件｜业务记录只生成一次且内容可读取
【处理中】暂停后恢复任务｜已完成项不重复执行
```

## 常见错误

| 错误做法 | 问题 | 替代做法 |
|---|---|---|
| 第一层按“功能/边界/异常/安全/性能”分 | 同一业务链路被拆散，读者无法按场景执行 | 一级按产品/角色/入口，方法体现在测试点与标题 |
| 每种输入格式或实现方式一个目录 | 目录爆炸、组合层级过深 | 在标题或标签中表达交叉维度 |
| 用接口名、字段名或枚举值作为目录 | 业务人员无法理解，且目录随实现频繁变化 | 改为用户可感知的阶段或状态 |
| 为每条用例建一个文件夹 | 层级无信息量、维护成本高 | 测试点直接挂用例；只有状态/阶段才建组 |

## 重组已有用例

1. 先列出当前所有一级/二级目录，标注它实际表达的维度（产品？版本？状态？方法？模块？）。
2. 找出维度混用的层，根据执行入口和最强业务分支确定该层的“唯一分类问题”。
3. 建立旧父节点到新父节点的映射后重排；被删除目录中的用例必须全部有归属，不能丢失。
4. 通过 ai-mind-map MCP 完成移动、新增或删除，操作后重新读取全量结构，核对每条用例都在正确位置。
5. 重排后核对用例 ID 集合完全一致，再运行 `validate-test-cases.js`，确认没有新增空业务分组和重复标题。
