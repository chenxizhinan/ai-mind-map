# Review 与质量门禁

输出前必须做一次**全量 Review**（不是抽样）。目标：发现覆盖缺口、伪用例、重复用例、不可执行用例与优先级失真。

## 一、模式与范围

- [ ] 已明确本次是新建设计、增量补充、层级重组还是只读评审。
- [ ] 只读评审没有产生写操作；重组没有改变用例语义和稳定 ID。
- [ ] 测试对象、版本、角色、环境、测试层级、范围内和范围外内容已明确。

## 二、测试分析与追溯

- [ ] 每条范围内事实已形成测试条件，或明确标记待确认/范围外。
- [ ] 每个测试条件有事实来源、判定依据、风险和适用测试方法。
- [ ] 高风险测试条件均有用例；部分覆盖和未覆盖项已列出。
- [ ] 每条用例在 `remark` 中有稳定用例 ID、来源和测试条件 ID。
- [ ] `CASE-*` 在同一文档内没有重复；同一 `TCND-*` 下超过 4 条用例时，确认条件不是模块级粒度。
- [ ] 没有把当前实现现象直接当作唯一测试预言。

## 三、结构检查

- [ ] 每一层只表达一个分类维度；没有把测试方法混进业务目录。
- [ ] 层级主轴符合执行和查找习惯；层级深度不超过 5 层，每层有明确收益。
- [ ] 没有用接口路径、字段名、枚举值、表名或内部组件名做业务目录。
- [ ] 没有无意义的空业务分组；有详情的测试资料/准备工作节点未被误删。
- [ ] 每条用例只挂在一个叶子测试点下，没有重复挂载。
- [ ] 数据类型、输入格式和实现差异等交叉维度在标题或标签中，而不是继续增加目录。

## 四、字段与可执行性

- [ ] 标题、前置条件、步骤、预期、优先级、用例类型、备注/来源齐全。
- [ ] 标题和目录只使用业务语言；接口、字段、枚举、权限、协议、内部模型和英文专业词已移到技术步骤/预期/备注。
- [ ] 单看标题即可理解条件、动作和主要结果；没有重复父级业务域，没有因过长而把多个断言塞进标题。
- [ ] 空前置条件有明确“无”的结论，而不是遗漏。
- [ ] 空步骤、空预期不存在。
- [ ] 步骤可执行；没有“执行对应操作”“按需求验证”等模板化描述。
- [ ] 预期可观察、可判定；没有“功能正常/符合预期/无异常”。
- [ ] 一条用例只有一个主要测试目标；多个断言共同证明该目标，互不依赖的目标已拆分。
- [ ] 前置状态可构造；不能构造的已标注“待确认”。
- [ ] 标题、详情、前置、步骤、预期和备注无 `�`、错误编码、未解码 HTML 实体或截断尾缀。

## 五、重复与伪用例

- [ ] 没有重复标题（规范化后相同）。
- [ ] 没有高度重复的步骤/预期（只改名称、不改内容的用例）。
- [ ] 不同版本、运行环境或实现方式的用例不是只改名称的复制品；差异点必须写进步骤或预期。
- [ ] 没有“检查页面存在”“打开页面”这类无判定的伪用例。
- [ ] 没有把同一测试点拆成多条无信息量用例来充数。

## 六、覆盖检查

- [ ] 已按适用性选择方法；不适用的方法没有被机械套用。
- [ ] 核心链路有成功流 + 主要异常/恢复路径。
- [ ] 状态机覆盖合法与非法转换、重复事件、取消或回滚、半完成状态。
- [ ] 边界值覆盖上下边界内外、空值、超长、临界并发。
- [ ] 权限/版本/开关组合覆盖关键组合与越权。
- [ ] 故障注入后核对所有权威数据源与外部副作用的一致性。
- [ ] 安全覆盖水平/垂直越权、跨租户隔离、凭证与日志脱敏。
- [ ] 兼容矩阵覆盖关键版本组合且内容确有差异。
- [ ] 性能用例给出容量/并发/阈值。
- [ ] 必要时核对页面、接口、持久化数据和外部副作用，而不只是页面展示。
- [ ] 多条件组合说明了全组合、判定表、Pairwise 或代表性抽样策略。
- [ ] 测试层级与测试类型没有混用；端到端只覆盖必要的跨边界核心链路。
- [ ] 适用的性能、可靠性、安全、兼容性、可访问性或国际化用例有明确标准。

## 七、优先级检查

- [ ] P0 逐条通过“影响、范围、恢复、决策”四问；“失败禁止发布”没有被当成自证理由。
- [ ] P0/P1 均有独立风险依据；未使用固定比例反向定级。
- [ ] 同一业务风险在页面、接口、服务、数据库或兼容组合中没有重复设置多个 P0；P0 是最小发布门禁集。
- [ ] 若范围包含核心主链路，已有相应 P0；低风险专项没有被强制补 P0。
- [ ] 数据一致性、租户隔离、不可逆操作没有被低估。
- [ ] 仅展示/低频防御场景没有被错误标成 P0。
- [ ] 每条 P0/P1 在 `remark` 说明失败影响或定级理由。
- [ ] P0/P1 都有完整步骤和明确断言。
- [ ] 同一分组全部 P0 时，每条都有独立阻断理由；优先级与发布门禁一致。
- [ ] 已报告 P0/P1/P2/P3 数量与 P0 占比；P0 超过 35% 或分组全部 P0 时已逐条复核并记录结论。
- [ ] 无法确认的定级已标记待确认，没有机械上调。

## 八、事实来源

- [ ] 需求/RFC/接口/代码/历史缺陷已阅读，已实现/计划实现/待确认已区分。
- [ ] 若涉及测试平台已有功能：已只读查询历史用例，识别历史测试面（回归点/同类风险/覆盖缺口）；平台旧用例未被直接修改。
- [ ] 没有臆测产品行为；不确定项标记“待确认”并说明缺失来源。
- [ ] 每组用例 `remark` 保留需求编号/Reference/接口/代码路径。

## 九、确定性校验

运行：

```bash
node .agents/skills/test-case-designer/scripts/validate-test-cases.js <mindmap.json 或目录> [--strict]
```

- ERROR 必须修复并重跑。
- WARN 逐条判断；可接受的要在 Review 结论中说明原因。
- 默认会提示 P0 占比超过 35% 和同一直接分组 3 条以上全部 P0；这是复核触发器，不是比例配额。
- 建议在 MCP 写入后、最终回复前执行，避免把问题留给下一位评审者。

## 十、退出标准

以下全部满足才算完成：

1. 无 ERROR；WARN 已逐条处理或解释。
2. 模式和修改范围符合授权；重组前后 ID 与数量已核对。
3. 层级符合决策规则，无无意义空分组、无实现名业务目录。
4. 每条用例字段完整、可执行、可判定、无意外重复。
5. 范围内事实与高风险测试条件有追溯和覆盖，剩余风险已报告。
6. P0/P1 定级有依据，分布与范围和发布策略一致。
7. 已向用户报告数量、追溯覆盖、门禁结果与待确认项。
