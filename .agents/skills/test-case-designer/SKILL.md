# 测试用例设计 Skill

目标不是“生成更多用例”，而是做对四件事：

1. 先把事实、风险、测试条件和判定依据分析清楚，再决定写哪些用例。
2. 根据需求选择正确的层级维度，而不是套固定模板。
3. 根据风险合理分配 P0–P3，而不是默认全 P0。
4. 识别“看起来很多、实际重复或不可执行”的伪用例。

本文件只保留入口、边界与主流程；详细规范按需加载 `references/` 中的文件，确定性检查优先用 ai-mind-map MCP 的 `validate_document` 工具（不可用时降级为运行 `scripts/validate-test-cases.js`）。

## 适用范围

支持：
- 从需求、RFC、接口文档、页面/交互设计、代码和历史缺陷生成手工测试用例。
- 重组已有用例的层级与归属。
- 评审覆盖缺口、重复用例、不可执行用例与优先级失真。
- 通过 ai-mind-map MCP 写入/更新脑图文档。
- 产出结构清晰、可执行、可判定且可追溯的手工用例。
- 建立并维护用例集的测试准备区（测试输入、测试范围、测试环境与测试数据）。

不负责：
- 执行测试。
- 编写自动化数据集或脚本。
- 修改产品代码。
- 发现问题后直接提交缺陷（只记录，不越权提交）。

## 输入与事实来源

生成前必须先读事实来源，并区分 **已实现 / 计划实现 / 待确认**：

- 需求、RFC、验收标准、Reference / Guide 文档。
- 接口定义、状态码、鉴权与数据模型。
- 页面交互与权限入口。
- 相关代码实现、配置开关、数据库模型（必要时）。
- 历史缺陷与线上问题（用于错误推测和风险判断）。

无法从事实源确认的行为，标记为“待确认”，不得自行编造；每组用例在 `remark` 保留来源（需求编号 / Reference / 接口名 / 代码路径）。

## 工作模式

开始前按 `references/operation-modes.md` 选择且只选择一个主模式：

- **新建设计**：从事实源建立测试分析、层级和用例。
- **增量补充**：保留稳定节点和用例 ID，只补覆盖缺口或受影响范围。
- **层级重组**：调整导航结构但不改变用例语义、数量和标识；发现内容缺口只报告，不擅自扩写。
- **只读评审**：只输出问题、证据和建议，不写入、不移动、不删除节点。

用户仅要求 review、检查或建议时，默认使用只读评审；只有用户明确要求新增、修改、整理或修复时才执行写操作。

## 主流程

1. **选择工作模式**：按 `references/operation-modes.md` 明确本次允许读取和修改的范围。
2. **确定测试对象与边界**：明确版本、角色、环境、测试层级、范围外内容和本次必须覆盖的核心链路。
3. **形成测试分析**：按 `references/test-analysis-standard.md` 提取事实来源、测试条件、风险、判定依据、数据/环境和待确认项。范围大、条件多或事实冲突时，先向用户展示分析摘要再写用例；小范围且事实清晰的修改可在同一次执行中完成。
   如果本次变更涉及测试平台已有功能，先用 test-platform MCP **只读查询**相关模块的历史用例（`search_version_test_cases` / `get_version_test_case`），识别历史测试面：哪些历史验证过的行为可能被本次改动破坏（回归点）、历史异常/边界用例是否预示同类风险、历史覆盖缺了哪些测试面。**平台旧用例不直接修改**——发现的问题写进脑图（回归测试点/新用例，remark 引用平台用例 ID 作来源），平台侧维护由用例负责人按平台流程处理。
4. **建立测试准备区**：按 `references/test-readiness-standard.md` 创建并整理「00 测试准备」分区——测试输入（需求与设计来源）、测试范围（范围内/外）、测试环境准备、测试数据准备。新建设计必须完整建立；增量补充时缺失则主动补建；测试输入、范围或环境/数据发生变化时同步更新，保持与用例树一致（范围内的模块与一级分支一一对应）。
5. **建立追溯关系**：按 `references/traceability-standard.md` 把事实来源映射到测试条件和用例，识别未覆盖来源与无来源用例。
6. **获取方法约束**：设计或大幅重组用例时调用 `get_test_methods`，结合当前文档约束选择方法；小范围文字修订无需重复调用。
7. **选择层级维度**：按 `references/hierarchy-standard.md`。依据执行入口和最强业务分支选择主轴；树负责导航，交叉覆盖由标题、标签或追溯信息表达。
8. **选择测试设计方法**：按 `references/test-design-methods.md` 选择适用方法，不要机械套满全部维度或生成笛卡尔积。
9. **写用例**：按 `references/case-writing-standard.md`。标题体现一个主要测试目标；背景和数据说明放详情；来源、接口和内部状态码放备注。
10. **定级与校准**：按 `references/priority-standard.md` 逐条判断影响范围、可恢复性、绕行能力和发布决策；再检查同一风险是否被多个 P0 重复表达。占比只用于触发复核，不得按固定比例反向改级。
11. **按模式执行**：需要写入时只通过 ai-mind-map MCP 修改目标文档；只读评审不得产生写操作。调用 `query_tree`、`add_subtree`、`update_node`、删除、批注、导出、方法库或校验工具时，每次都显式传入本次确认的 `docId`，不得依赖共享的 active 文档状态。
12. **全量 Review 与质量门禁**：按 `references/review-checklist.md` 自查。必须报告优先级分布并逐组复核异常 P0；不能只确认字段齐全。然后运行确定性校验：

   ```bash
   node .agents/skills/test-case-designer/scripts/validate-test-cases.js <mindmap.json 或目录> [--strict]
   ```

   有 ERROR 必须修复后重跑；WARN 逐条判断是否可接受并说明理由。

## 不可妥协的规则

- **层级和标题使用业务语言**：目录及用例标题必须让非研发执行者直接读懂；接口名、字段名、枚举值、表名、权限标识、协议词和内部组件名只放在备注、技术步骤或契约断言中。
- **标题一眼可懂**：用自然业务句式写清“条件、动作、主要结果”，例如“迁移暂停后恢复任务，已完成文件不重复复制”；不重复父级分类、不堆技术断言，一个用例只有一个主要测试目标，标题最多 100 个字符。
- **禁止臆测**：产品行为必须以需求/接口/代码为依据；不确定就标记“待确认”。
- **禁止交付损坏文本**：写入后必须检查标题、详情、前置、步骤、预期和备注中的替换字符、错误编码、HTML 实体及截断符；不能把界面截断文本当成正式内容。
- **优先级是风险判断**：不允许机械按“正常=P0、异常=P1、边界=P2”分配；同一分组全部 P0 时，每条都必须有独立阻断理由。
- **P0 是最小发布门禁集**：同一核心风险的成功流、异常流、兼容组合和实现层验证不能全部标为 P0；保留能代表发布承诺的最小集合，其余按风险降为 P1/P2。
- **禁止循环论证**：备注仅写“失败禁止发布”“属于核心链路”不能证明 P0；必须说明影响对象与范围、是否可恢复/回滚/绕行，以及为什么本次发布不能接受该风险。
- **P0/P1 必须可执行、可判定**：具备完整步骤与明确断言，不能写概念性检查。
- **追溯 ID 是唯一标识**：`CASE-*` 在同一文档内必须唯一，复用到不同用例属于 ERROR；`TCND-*` 表达可独立验证的行为，不是模块名，同一条件下超过 4 条用例时应拆分更细条件。
- **平台历史用例只读**：test-platform 的旧用例是历史测试面参考，不直接修改；研发产出落在脑图（回归点 + 新用例 + 其他测试面检查），平台用例的维护走平台自身流程。
- **影响面清单按方案判断**：影响面清单（数据一致性、幂等、并发、权限、兼容、性能、可观测、回滚等 17 项）是分析需求和技术方案时的思考清单，不是每个需求都会涉及；按最终实现方案判断哪些面被触发，被触发的面评估是否补充用例，不涉及的不写用例。
- **用例集自带测试准备区**：新建设的用例集必须包含「00 测试准备」分区（测试输入、测试范围、测试环境准备、测试数据准备）且四项齐备；既有文档缺失时，增量补充模式下主动补建并填充已知信息。
- **不绕过 MCP**：写脑图只走 MCP 工具；发现问题记录在 `remark` 或批注中，不直接改文件，也不自动提交缺陷。

## 输出报告

完成后向用户报告（简明）：

- 文档 / 模块 / 用例数量，各优先级数量与 P0 占比。
- 工作模式、测试范围、事实来源和追溯覆盖情况。
- 测试准备区状态：测试输入 / 范围 / 环境准备 / 数据准备四项是否齐备，未就绪项与负责人。
- 覆盖了哪些测试方法与关键风险（数据一致性、租户隔离、不可逆操作、兼容矩阵等）。
- 影响面评估结论：本次方案触发了哪些面（对应什么用例/检查表节点）、明显可能被问到但未触发的面（简要说明为何不涉及）。
- 质量门禁结果：ERROR / WARN 数量与处理方式。
- 若参考了 test-platform 历史用例：说明识别到的历史测试面、回归范围和其他测试面结论。
- 仍存在的“待确认”项与建议补充的信息来源。
- 若重组了层级：说明新的层级决策依据。

## MCP 写入原则

1. 先用 `list_documents` 确认目标文档，再用 `open_document` 的返回值锁定准确 `docId`；后续每一次文档内工具调用都传同一个 `docId`。多文档模式缺少 `docId` 时 MCP 会拒绝执行，避免多 Agent 或交叉操作串文件。
2. 批量新增优先提交完整子树，局部修改只更新目标节点，重组时保留全部原用例的归属关系。
3. 删除或覆盖内容前确认影响范围；不可恢复的操作必须获得用户明确授权。
4. 写入后重新读取全量结构，核对节点数、层级、空分组和用例归属，再运行确定性校验。
